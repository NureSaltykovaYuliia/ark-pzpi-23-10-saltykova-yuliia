　　　1 ОПИС ІНЖЕНЕРНИХ РІШЕНЬ
　　　1.1. Архітектурні рішення
　　　Під час розробки серверної частини застосовано підхід Clean Architecture, який дозволяє чітко розмежувати бізнес логіку, доступ до даних та інтерфейс взаємодії з клієнтом. Така структура забезпечує гнучкість, масштабованість і легкість у тестуванні застосунку.
　　　Використані архітектурні патерни:

　　　Repository Pattern — створено універсальний рівень доступу до даних, який приховує деталі реалізації бази даних. Це спрощує тестування та підвищує гнучкість при зміні ORM чи СУБД.
　　　Dependency Injection (DI) — усі сервіси та репозиторії впроваджуються через конструктор, що зменшує зв’язність компонентів і дозволяє легко замінювати реалізації.
　　　DTO Pattern — забезпечує передачу лише необхідних даних між шарами системи, приховуючи внутрішні деталі моделі та захищаючи систему від надмірного розкриття інформації.
　　　Controller-Service-Repository Structure — контролери відповідають лише за обробку HTTP-запитів, бізнес логіка розміщена у сервісах, а робота з даними — у репозиторіях.
　　　Взаємодія шарів системи:
1.Користувач надсилає HTTP-запит до контролера.
2.Контролер викликає відповідний метод сервісу, що містить бізнес логіку.
3.Сервіс взаємодіє з репозиторієм, який звертається до бази даних через Entity Framework Core.
4.Результат передається назад у вигляді DTO-об’єкта.

　　　Такий підхід дозволяє легко розширювати систему, наприклад, додавати нові модулі (чат, аналітику, тощо), не порушуючи існуючу логіку.
　　　1.2 Вибір технологій та інструментів
　　　Основні технології:
　　　Таблиця 1.1 - Основні технології

Технологія	Призначення
.NET	Платформа розробки серверної частини
ASP.NET Core	Framework для створення RESTful API
Entity Framework Core	ORM для роботи з базою даних
SQLite	Вбудована СУБД для локальної розробки
JWT Bearer	Механізм аутентифікації та авторизації
BCrypt.Net	Хешування паролів користувачів
Swagger / OpenAPI	Генерація документації до API
　　　
　　　Обґрунтування вибору:

　　　ASP.NET Core — сучасний, кросплатформений фреймворк, що забезпечує високу продуктивність і має вбудовану підтримку DI, middleware, авторизації та аутентифікації.
　　　
　　　Entity Framework Core — надає зручний Code-First підхід до роботи з базою даних, підтримує LINQ-запити та забезпечує автоматичні міграції.
　　　SQLite — легка, проста у використанні БД, яка не потребує окремого серверу, ідеальна для навчальних проєктів.
　　　JWT (JSON Web Token) — забезпечує безпечну аутентифікацію без необхідності зберігання сесій на сервері.
　　　BCrypt — гарантує безпечне зберігання паролів шляхом хешування.
　　　Swagger — дозволяє автоматично створювати інтерактивну документацію, полегшує тестування API.
　　　1.3 Реалізована бізнес логіка
　　　Бізнес логіка системи складається з декількох модулів, одними з яких є управління розумними пристроями та управління користувачами.
　　　
　　　Управління розумними пристроями
　　　Основні функції:
　　　-Реєстрація нового пристрою, прив’язаного до собаки.
　　　-Оновлення координат пристрою та стану батареї.
　　　-Перегляд усіх пристроїв, що належать користувачу.
　　　-Видалення пристрою при видаленні собаки.
　　　Бізнес правила:
　　　-Один пристрій може бути прив’язаний лише до однієї собаки.
　　　-Користувач має доступ лише до пристроїв, які належать його собакам.
　　　-Адміністратор має доступ до всіх пристроїв у системі.
　　　
　　　
　　　Алгоритм створення пристрою:
　　　-Перевірити, чи існує собака з указаним ID.
　　　-Перевірити, чи належить собака поточному користувачу.
　　　-Переконатися, що пристрій ще не прикріплений.
　　　-Створити пристрій з початковими параметрами (координати = 0, заряд = 100%).
　　　-Зберегти об’єкт у базі даних.
　　　
　　　Управління користувачами
　　　Основні функції:
　　　-Перегляд і редагування власного профілю.
　　　-Збереження геолокації користувача.
　　　-Відображення статистики активності.
　　　-Видалення користувача разом із пов’язаними даними.
　　　Бізнес правила:
　　　-При кожному зверненні оновлюється поле LastActivity.
　　　-Заблоковані користувачі не можуть редагувати профіль чи виконувати дії в системі.
　　　-Видалення користувача призводить до каскадного видалення його даних.
　　　1.4 Функції адміністрування
　　　Система передбачає окремий набір можливостей для адміністраторів, спрямованих на керування користувачами та підтримання безпеки.
　　　
　　　
　　　
　　　Основний функціонал:

　　　Отримання статистики користувачів
　　　-Загальна кількість користувачів.
　　　-Кількість активних за останні 30 днів.
　　　-Кількість заблокованих акаунтів.
　　　-Кількість адміністраторів та звичайних користувачів.
　　　
　　　Моніторинг активності
　　　-Перегляд останнього входу користувачів.
　　　-Відстеження статусу блокування та причини блокування.
　　　-Блокування / розблокування користувачів
　　　-Адміністратор може заблокувати користувача, вказавши причину.
　　　-Заблоковані користувачі не можуть виконувати жодні дії.
　　　-Адміністратор може розблокувати користувача в будь-який момент.
　　　Рольова модель доступу
　　　-Реалізовано ролі: DogOwner, Admin.
　　　-Для захищених endpoint’ів використовується [Authorize(Roles = "Admin")].
　　　-Ролі зберігаються в JWT-токені та перевіряються при кожному запиті.
　　　
　　　

　　　

　　　
　　　2  ФРАГМЕНТИ ПРОГРАМНОГО КОДУ
　　　У цьому розділі наведено приклади основних частин бізнес логіки та адміністративних функцій із коротким поясненням.
　　　2.1 Бізнес логіка
　　　Створення пристрою:
　　　Метод створює новий пристрій, перевіряє власника собаки та гарантує, що до неї не прив’язано інший пристрій.
　　　public async Task<SmartDeviceDto> CreateDeviceAsync(CreateSmartDeviceDto deviceDto, int userId)
　　　{
　　　    var dog = await _dogRepository.GetByIdAsync(deviceDto.DogId);
　　　    if (dog == null)
　　　        throw new Exception("Собака не знайдена");
　　　
　　　    if (dog.OwnerId != userId)
　　　        throw new UnauthorizedAccessException("Ви не маєте доступу до цієї собаки");
　　　
　　　    var existingDevice = await _deviceRepository.GetByDogIdAsync(deviceDto.DogId);
　　　    if (existingDevice != null)
　　　        throw new Exception("До цієї собаки вже прикріплений пристрій");
　　　
　　　    var device = new SmartDevice
　　　    {
　　　        DeviceGuid = deviceDto.DeviceGuid,
　　　        DogId = deviceDto.DogId,
　　　        LastLatitude = 0,
　　　        LastLongitude = 0,
　　　        BatteryLevel = 100
　　　    };
　　　
　　　    var createdDevice = await _deviceRepository.AddAsync(device);
　　　    return MapToDto(createdDevice, dog.Name);
　　　}
　　　
　　　Оновлення пристрою:
　　　Оновлює координати та рівень заряду пристрою, перевіряючи права користувача.
　　　public async Task UpdateDeviceAsync(int id, UpdateSmartDeviceDto deviceDto, int userId)
　　　{
　　　    var device = await _deviceRepository.GetByIdAsync(id);
　　　    if (device == null)
　　　        throw new Exception("Пристрій не знайдено");
　　　
　　　    var dog = await _dogRepository.GetByIdAsync(device.DogId);
　　　    if (dog.OwnerId != userId)
　　　        throw new UnauthorizedAccessException("Ви не маєте доступу до цього пристрою");
　　　
　　　    device.LastLatitude = deviceDto.LastLatitude;
　　　    device.LastLongitude = deviceDto.LastLongitude;
　　　    device.BatteryLevel = deviceDto.BatteryLevel;
　　　
　　　    await _deviceRepository.UpdateAsync(device);
　　　}
　　　2.2  Адміністрування
　　　Блокування користувача:
　　　Метод блокує користувача, якщо він не є адміністратором, і зберігає причину блокування в базі даних.
　　　
public async Task<bool> BlockUserAsync(int userId, string blockReason)
　　　{
　　　    var user = await _userRepository.GetUserByIdAsync(userId);
　　　    if (user == null)
　　　        throw new Exception("Користувача не знайдено.");
　　　
　　　    if (user.Role == UserRole.Admin)
　　　        throw new Exception("Не можна заблокувати адміністратора.");
　　　
　　　    user.IsBlocked = true;
　　　    user.BlockReason = blockReason;
　　　
　　　    await _userRepository.UpdateUserAsync(user);
　　　    return true;
　　　}
　　　
　　　Отримання статистики користувачів:
　　　
　　　Метод підраховує кількість усіх користувачів, активних за останні 30 днів і заблокованих облікових записів.
　　　public async Task<UserStatisticsDto> GetUserStatisticsAsync()
　　　{
　　　    var users = await _userRepository.GetAllUsersAsync();
　　　    var now = DateTime.UtcNow;
　　　    var monthAgo = now.AddDays(-30);
　　　
　　　    return new UserStatisticsDto
　　　    {
　　　        TotalUsers = users.Count,
　　　        ActiveUsers = users.Count(u => u.LastActivity >= monthAgo),
　　　        BlockedUsers = users.Count(u => u.IsBlocked),
　　　        TotalAdmins = users.Count(u => u.Role == UserRole.Admin),
　　　        TotalRegularUsers = users.Count(u => u.Role == UserRole.DogOwner)
　　　    };
　　　}
Розблокування користувача:
Розблоковує користувача, очищаючи причину блокування.
public async Task<bool> UnblockUserAsync(int userId)
{
    var user = await _userRepository.GetUserByIdAsync(userId);
    if (user == null)
        throw new Exception("Користувача не знайдено.");

    user.IsBlocked = false;
    user.BlockReason = null;

    await _userRepository.UpdateUserAsync(user);
    return true;
}



3 UML ДІАГРАМИ
3.1 UML діаграма діяльності

Створення розумного пристрою

　　　
Рисунок 3.1 - UML діаграма діяльності
　　　
　　　
　　　Покроковий опис логіки, зображеної на діаграмі:
　　　
　　　Початок (Ініціація): Процес починається з дій користувача поза системою: він додає собаку у свій профіль та отримує фізичний розумний пристрій.
　　　Запит до API: Користувач ініціює прив'язку пристрою, надсилаючи POST-запит на ендпоінт /api/smartdevices, передаючи ідентифікатори пристрою (deviceGuid) та собаки (dogId).
　　　Авторизація: Система перехоплює запит і насамперед виконує перевірку JWT токену та авторизацію користувача.
　　　Якщо токен невалідний (Ні): Процес негайно завершується. Користувач отримує відповідь 401 Unauthorized.
　　　Запуск бізнес-логіки:
　　　Якщо токен валідний (Так): Система викликає внутрішній метод CreateDeviceAsync().
　　　Перевірка собаки:
　　　Виконується пошук собаки за dogId у базі даних.
　　　Якщо собака не існує (Ні): Генерується виняток (Exception) "Собака не знайдена", і користувач отримує відповідь 400 BadRequest.
　　　Перевірка власності:
　　　Якщо собака існує (Так): Виконується критична перевірка безпеки: чи ID власника собаки (dog.OwnerId) збігається з ID користувача (userId) з токена.
　　　Якщо власник не збігається (Ні): Генерується виняток UnauthorizedAccessException ("Не ваша собака"), і користувач отримує відповідь 403 Forbidden.
　　　Перевірка на дублікат:
　　　Якщо користувач є власником собаки (Так): Система перевіряє, чи для цієї собаки вже зареєстрований інший пристрій.
　　　Якщо пристрій вже існує (Так): Генерується виняток "Пристрій вже існує", і користувач отримує відповідь 400 BadRequest.
　　　Успішне створення (Happy Path):
　　　Якщо пристрій ще не існує (Ні):
　　　Створюється новий об'єкт SmartDevice з переданими DeviceGuid та DogId.
　　　Встановлюються початкові значення: LastLatitude = 0, LastLongitude = 0, BatteryLevel = 100.
　　　Новий пристрій додається асинхронно (AddAsync(device)).
　　　Зміни зберігаються в базі даних.
　　　Об'єкт пристрою перетворюється (мапиться) у DTO (Data Transfer Object).
　　　Користувачу повертається відповідь 201 Created разом з даними про новостворений пристрій.
　　　Завершення: Усі гілки процесу (успішне створення або помилки 400, 401, 403) сходяться до точки завершення.
　　　
　　　
　　　
　　　
　　　
　　　
　　　
　　　
　　　
　　　
　　　
　　　
3.2 UML діаграма послідовності

Створення розумного пристрою


Рисунок 3.2 - UML діаграма послідовності
　　　
　　　Ця діаграма ілюструє взаємодію між різними компонентами системи  під час обробки запиту на створення нового пристрою.
　　　



　　　Учасники :
　　　
　　　Користувач: Актор, який ініціює запит.
　　　SmartDevicesController: Шар API (Presentation), що приймає HTTP-запит.
　　　SmartDeviceService: Шар бізнес-логіки (Application), що координує процес.
　　　DogRepository: Шар інфраструктури, що відповідає за доступ до даних про собак.
　　　SmartDeviceRepository: Шар інфраструктури, що відповідає за доступ до даних про пристрої.
　　　Database: База даних, де зберігаються дані.
　　　
　　　Покроковий опис процесу
　　　Ініціація запиту:
　　　Користувач надсилає POST /api/smartdevices запит до SmartDevicesController з даними {deviceGuid: "ABC-123", dogId: 5}.
　　　Аутентифікація та Авторизація:
　　　SmartDevicesController валідує JWT токен, що надійшов із запитом, та витягує з нього userId (ID поточного користувача).
　　　Виклик бізнес-логіки:
　　　Контролер викликає метод CreateDeviceAsync у SmartDeviceService, передаючи йому DTO з даними запиту та userId.
　　　Перевірка власності собаки (Бізнес-логіка):
　　　SmartDeviceService звертається до DogRepository з запитом GetByIdAsync(5), щоб отримати дані про собаку.
　　　DogRepository виконує SELECT * FROM Dogs WHERE id = 5 до Database.
　　　База даних повертає Dog entity (об'єкт собаки).
　　　SmartDeviceService виконує ключову перевірку: dog.OwnerId == userId. Це перевірка прав власності, яка гарантує, що користувач може додавати пристрої лише для своїх собак.
　　　Перевірка на дублікат пристрою:
　　　Після успішної перевірки власності, SmartDeviceService звертається до SmartDeviceRepository з запитом GetByDogIdAsync(5), щоб перевірити, чи у цієї собаки вже є пристрій.
　　　SmartDeviceRepository виконує SELECT * FROM SmartDevices WHERE DogId = 5 до Database.
　　　База даних повертає null, що означає "пристрою не існує".
　　　Створення та збереження об'єкта:
　　　SmartDeviceService (переконавшись, що пристрою ще немає) створює новий об'єкт SmartDevice з початковими даними (включаючи BatteryLevel: 100, LastLatitude: 0 і т.д.).
　　　Сервіс викликає метод AddAsync(device) у SmartDeviceRepository.
　　　SmartDeviceRepository виконує команду INSERT INTO SmartDevices VALUES (...) у Database.
　　　База даних зберігає об'єкт і повертає Device with ID (новий об'єкт з присвоєним ID).
　　　Формування відповіді:
　　　SmartDeviceService отримує від репозиторію збережену SmartDevice entity.
　　　Сервіс виконує перетворення в DTO (MapToDto), готуючи дані для відповіді користувачу.
　　　DTO повертається до SmartDevicesController.
　　　
　　　
　　　
　　　Відповідь користувачу:
　　　SmartDevicesController формує успішну HTTP-відповідь 201 Created і надсилає її Користувачу разом з даними про створений пристрій (SmartDeviceDto).
