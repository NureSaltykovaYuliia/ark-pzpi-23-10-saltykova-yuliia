1  ОПИС ІНЖЕНЕРНИХ РІШЕНЬ
　　　1.1 Опис архітектурних рішень IoT клієнта.
　　　Розроблений IoT клієнт є програмним забезпеченням для мікроконтролера ESP32, написаним мовою MicroPython. Архітектура проекту спроєктована за модульним принципом, що дозволяє розділити відповідальність між різними компонентами системи, полегшуючи налагодження, тестування та подальше розширення функціоналу.
　　　Структура проекту складається з наступних незалежних модулів:
　　　Модуль керування (main.py): Виступає точкою входу в програму. Він відповідає за ініціалізацію апаратних компонентів (LED індикаторів), виклик функцій підключення до мережі та запуск головного робочого циклу (Main Loop). Цей файл об'єднує всі інші компоненти в єдину працюючу систему.
　　　Модуль конфігурації (config.py): Містить усі налаштування системи, винесені в окремий файл. Це включає параметри WiFi (WIFI_SSID, WIFI_PASSWORD), базові URL для API, інтервали оновлення даних та параметри геозони. Такий підхід дозволяє змінювати поведінку пристрою без необхідності правки коду бізнес-логіки.
　　　Менеджер пристрою (device_manager.py): Інкапсулює логіку взаємодії з REST API сервера. Він приховує деталі HTTP-запитів від основного циклу, надаючи високорівневі методи для реєстрації пристрою та відправки телеметрії.
　　　Сенсорні модулі (gps_sensor.py, battery_monitor.py): Відповідають за отримання даних. Оскільки робота виконується в симуляторі, модуль GPS реалізує алгоритм "Random Walk" (випадкове блукання) для імітації реалістичного переміщення собаки, а модуль батареї симулює поступове розряджання та процес зарядки.
　　　Модуль геозони (geofence_monitor.py та geo.py): Виконує математичні обчислення для визначення відстані між поточними координатами та центром безпечної зони, використовуючи формулу Haversine, яка враховує кривизну Землі.
　　　1.2. Пояснення вибору методів комунікації та мережевих протоколів
　　　Для організації зв'язку між IoT пристроєм та серверною частиною було обрано архітектурний стиль REST та протокол прикладної ланки HTTP.
　　　Обґрунтування вибору протоколу HTTP:
　　　Сумісність з Backend: Серверна частина системи MyDogSpace побудована на ASP.NET Web API, яка нативно працює з HTTP запитами. Використання HTTP на клієнті дозволило уникнути необхідності розгортання додаткових проміжних вузлів, таких як MQTT брокер.
　　　Легкість реалізації: У середовищі MicroPython доступна бібліотека urequests, яка дозволяє реалізувати відправку даних кількома рядками коду, підтримуючи методи POST, PUT та GET.
　　　Керування станом: Використання стандартних кодів відповіді HTTP (наприклад, 204 No Content для успішної телеметрії або 404 Not Found) спрощує обробку помилок на стороні клієнта.
　　　Модель авторизації та безпеки: 
　　　(Особливістю інженерного рішення є відмова від JWT-авторизації для IoT пристрою в класичному розумінні.) Це рішення обґрунтовано наступним чином:
　　　IoT пристрій є "безголовим" (headless) і не має інтерфейсу для введення логіна/пароля користувача.
　　　API Endpoints для прийому телеметрії на сервері налаштовані з атрибутом [AllowAnonymous], але вимагають валідного deviceGuid та ідентифікатора пристрою в базі даних.
　　　Безпека забезпечується унікальністю GUID пристрою та перевіркою реєстрації на стороні сервера перед прийняттям даних.
　　　1.3. Опис бізнес-логіки
　　　Бізнес-логіка клієнта реалізована у вигляді кінцевого автомата (State Machine), який циклічно виконує послідовність дій. Алгоритм роботи включає наступні етапи:
　　　Ініціалізація та Реєстрація: При старті пристрій підключається до WiFi. Після цього він виконує "ідемпотентний" запит на реєстрацію (POST /api/smartdevices/register-device). Це означає, що запит можна виконувати багаторазово без ризику створення дублікатів. Сервер повертає внутрішній ID пристрою, який зберігається в пам'яті для подальших запитів.
　　　
　　　Рисунок 1.1 - Реєстрація та ініціалізація
　　　Прив’язуємо собаку до пристрою:
　　　
　　　
　　　
　　　Рисунок 1.1 - Прив’язуємо собаку
　　　Моніторинг стану: У головному циклі пристрій опитує віртуальні сенсори. Для GPS застосовано алгоритм, де собака з ймовірністю 30% змінює напрямок руху, що дозволяє протестувати вихід за межі геозони.
　　　
　　　
　　　Рисунок 1.3 - Зміна напрямку руху
　　　Контроль геозони (Geofencing): На кожній ітерації обчислюється відстань від "дому". Якщо відстань перевищує заданий радіус (наприклад, 100 метрів), система переходить у стан "Тривога". Щоб уникнути спаму сповіщеннями, реалізовано логіку прапорців: сповіщення відправляється лише один раз при перетині межі, і скидається тільки після повернення в безпечну зону.
　　　
　　　
　　　Рисунок 1.4 - Вихід за межі геозони
　　　
　　　
　　　
　　　Відправка телеметрії: Зібрані дані (координати, заряд батареї) упаковуються в JSON-об'єкт та відправляються методом PUT на сервер. Інтервал відправки налаштовується (за замовчуванням 5-10 секунд для тестів), що дозволяє балансувати між актуальністю даних та енергоспоживанням.

　　　2 ФРАГМЕНТИ ПРОГРАМНОГО КОДУ
　　　
　　　2.1. Код бізнес-логіки IoT клієнта

　　　Бізнес-логіка IoT клієнта зосереджена на трьох основних процесах: зборі телеметричних даних, локальному аналізі безпеки (Geofencing) та синхронізації стану з сервером. Нижче наведено ключові фрагменти коду, що реалізують ці процеси, з детальним описом алгоритмів.
　　　2.1.1. Відправка телеметрії (device_manager.py)
　　　Ця функція є ядром комунікації пристрою. Вона агрегує дані з різних сенсорів та відправляє їх на сервер. Використання методу PUT обумовлено REST архітектурою: ми оновлюємо поточний стан ресурсу (пристрою) на сервері.
Код програми:
def send_telemetry(self):
    """
    Відправка телеметричних даних на сервер.
    Виконує агрегацію даних з GPS та сенсора батареї, серіалізує їх у JSON
    та відправляє через HTTP PUT запит.
    """
    # 1. Перевірка передумов: Неможливо відправити дані, якщо пристрій не має ID
    if not self.is_registered:
        print("[DEVICE] ✗ Пристрій не зареєстровано, пропуск такту")
        return False

    # 2. Агрегація даних: Отримання актуальних показників з модулів-сенсорів
    latitude, longitude = gps_sensor.read_coordinates()
    battery_level = battery_monitor.read_battery_level()

    # Перевірка валідності даних GPS (null check)
    if latitude is None or longitude is None:
        return False

    # 3. Формування Endpoint URL: Використання динамічного device_id
    url = f"{config.API_BASE_URL}{config.API_SMART_DEVICES}/device/{self.device_id}/telemetry"

    # 4. Підготовка Payload (Корисного навантаження)
    payload = {
        "lastLatitude": latitude,
        "lastLongitude": longitude,
        "batteryLevel": battery_level
    }

    try:
        # 5. Виконання запиту з обробкою мережевих виключень
        if config.DEBUG:
            print(f"[DEVICE] Sending PUT to {url}")

        response = urequests.put(
            url,
            headers={"Content-Type": "application/json"},
            data=ujson.dumps(payload)
        )

        # 6. Обробка відповіді: 204 No Content є стандартом успішного PUT запиту
        if response.status_code == 204:
            print(f"[DEVICE] ✓ Телеметрія відправлена успішно")
            response.close() # Важливо: звільнення сокету
            return True
        else:
            print(f"[DEVICE] ✗ Помилка відправки: статус {response.status_code}")
            response.close()
            return False

    except Exception as e:
        # Catch-all для помилок з'єднання (Connection Refused, Timeout)
        print(f"[DEVICE] ✗ Виняток при відправці телеметрії: {e}")
        return False


　　　Аналіз інженерного рішення:
　　　
　　　Відмовостійкість: Блок try-except гарантує, що при втраті Wi-Fi з'єднання програма не завершить роботу аварійно (crash), а лише пропустить одну ітерацію відправки.
　　　Оптимізація пам'яті: Використання response.close() є критичним для ESP32, оскільки кількість відкритих сокетів обмежена. Не закриття з'єднання призведе до помилки ENOMEM через декілька хвилин роботи.
　　　
　　　
　　　2.1.2. Моніторинг геозони та сповіщення (geofence_monitor.py)
　　　Цей модуль реалізує концепцію Edge Computing (обчислення на краю мережі). Замість того, щоб просто відправляти координати на сервер і чекати, поки сервер вирішить, чи є небезпека, пристрій самостійно приймає це рішення. Це зменшує затримку (latency) при виявленні небезпеки.

def check_position(self, latitude, longitude):
    """
    Алгоритм визначення безпеки поточної позиції.
    Використовує математичну модель Haversine для точного розрахунку відстані на сфері.
    """
    # Виклик математичної функції з модуля geo.py
    distance = geo.get_distance_meters(
        self.safe_zone_lat,    # Центр "дому"
        self.safe_zone_lon,
        latitude,              # Поточна позиція
        longitude
    )

    # Логічне порівняння з пороговим значенням
    is_safe = distance <= self.safe_zone_radius

    if config.DEBUG:
        status = "БЕЗПЕЧНО" if is_safe else "НЕБЕЗПЕКА!"
        print(f"[GEOFENCE] Відстань: {distance:.0f}м (Радіус: {self.safe_zone_radius}м) -> {status}")

    return (is_safe, distance)

def read_coordinates(self):
    """
    Генерація координат з використанням інерційної моделі руху.
    """
    if not self.is_active:
        return (None, None)

    # 1. Випадкова зміна курсу (імітація повороту тварини)
    # З імовірністю 30% курс змінюється на ±45 градусів
    if random.random() < 0.3:
        self.angle += random.uniform(-45, 45)

    # 2. Розрахунок вектору руху
    angle_rad = math.radians(self.angle)
    lat_change = self.step_size * math.cos(angle_rad)
    lon_change = self.step_size * math.sin(angle_rad)

    # 3. Застосування змін до поточних координат
    self.latitude += lat_change
    self.longitude += lon_change

　　　3 UML ДІАГРАМИ
　　　3.1. UML Діаграма прецедентів (Use Case Diagram)
　　　Діаграма ілюструє функціональні можливості системи з точки зору IoT пристрою як головного актора. Вона показує, які операції пристрій може ініціювати при взаємодії з сервером MyDogSpace.
　　　Опис діаграми:
　　　Актор: IoT Device (ESP32).
　　　Прецеденти (Use Cases):
　　　Підключення до WiFi: Базова умова для роботи.
　　　Реєстрація пристрою: Первинна ідентифікація в системі.
　　　Відправка телеметрії: Регулярна передача GPS та стану батареї.
　　　Перевірка геозони: Внутрішня логіка аналізу координат.
　　　Відправка сповіщення: Розширення прецеденту геозони, що виконується тільки при виявленні небезпеки (Include).
　　　
　　　Рисунок 3.1 - Діаграма прецедентів (Use Case Diagram)
　　　Основні елементи діаграми:
　　　1. Актори (Actors)
　　　Діаграма визначає три типи учасників взаємодії:
　　　IoT Пристрій (ESP32): Головний актор системи. Це фізичний пристрій, закріплений на собаці, який ініціює більшість процесів (зчитування сенсорів, відправка запитів).
　　　Серверна частина API: Зовнішня система (Secondary Actor), яка приймає REST-запити від пристрою, обробляє дані та зберігає їх у базі даних.
　　　Власник собаки: Користувач, який взаємодіє з системою опосередковано (через веб-інтерфейс), виконуючи налаштування та призначення собаки, що впливає на поведінку IoT пристрою.
　　　2. Ключові прецеденти (Use Cases)
　　　Всі сценарії використання можна розділити на логічні групи:
　　　А. Ініціалізація та підключення:
　　　Підключення до WiFi: Базовий сценарій, необхідний для початку роботи.
　　　Реєстрація пристрою на сервері: При першому запуску пристрій автоматично реєструється через endpoint /api/smartdevices/register-device без необхідності авторизації (як зазначено у примітці на діаграмі).
　　　Обробка помилок з'єднання: Розширює (extend) сценарії підключення та відправки даних, дозволяючи системі коректно реагувати на втрату мережі.
　　　Б. Конфігурація:
　　　Перевірка призначення собаки: Пристрій періодично опитує сервер, щоб дізнатися, чи прив'язав власник цей трекер до конкретної собаки. Це критично для початку збору статистики.
　　　Налаштування параметрів пристрою: Отримання конфігурації (наприклад, частоти оновлення даних) на основі дій власника.
　　　В. Робочий цикл (Телеметрія):
　　　Відправка телеметрії на сервер: Центральний прецедент. Він включає в себе (<<include>>) два обов'язкових підпроцеси:
　　　Зчитування GPS координат — отримання геоданих.
　　　Моніторинг рівня батареї — вимірювання заряду для запобігання повному розряду. Ці дані агрегуються та відправляються на сервер через асоціацію «communicate».
　　　Г. Безпека (Геозона):
　　　Перевірка геозони: Пристрій локально аналізує поточні координати відносно безпечного радіуса ("дому").
　　　Відправка сповіщення про небезпеку: Якщо перевірка геозони виявляє вихід за межі, спрацьовує цей прецедент (позначений як <<include>> або логічний наслідок перевірки), який негайно надсилає Alert на сервер.
　　　3. Відношення між елементами
　　　«communicate» (Асоціація): Показує передачу даних між IoT пристроєм та Сервером API (наприклад, при реєстрації, перевірці призначення та відправці телеметрії).
　　　«include» (Включення):
　　　Сценарій Відправка телеметрії завжди включає зчитування GPS та перевірку батареї, оскільки без цих даних відправка не має сенсу.
　　　Сценарій Перевірка геозони включає логіку Відправки сповіщення (у контексті даної діаграми це показує, що функція сповіщення є частиною модуля безпеки).
　　　«extend» (Розширення):
　　　Обробка помилок з'єднання розширює базові сценарії комунікації. Це означає, що обробка помилок виконується лише за певних умов (наприклад, коли WiFi.status() != CONNECTED), а не кожного разу.
　　　4. Примітки (Notes)
　　　На діаграмі додано пояснювальні записки, що уточнюють бізнес-логіку:
　　　Реєстрація відбувається автономно та без авторизації.
　　　Перевірка призначення собаки ініціюється пристроєм, але залежить від дій власника у веб-інтерфейсі.
　　　Геозона перевіряється для виявлення виходу собаки за межі безпечної території.

　　　3.2. UML Діаграма діяльності (Activity Diagram)
　　　Діаграма діяльності деталізує алгоритм роботи головного циклу програми (main_loop). Вона відображає послідовність кроків від увімкнення до обробки даних сенсорів.
　　　Опис алгоритму:
　　　Старт -> Ініціалізація мережі.
　　　Якщо мережа є -> Реєстрація пристрою.
　　　Вхід у безкінечний цикл while True.
　　　Зчитування координат (GPS) та заряду (Battery).
　　　Блок прийняття рішень (Condition): Чи знаходиться собака в безпечній зоні?
　　　Ні (Danger): Формування та відправка HTTP POST запиту з Alert.
　　　Так (Safe): Пропуск кроку сповіщення (або скидання прапорця тривоги).
　　　Безумовна відправка телеметрії (HTTP PUT).
　　　Затримка (Sleep) для економії енергії перед наступною ітерацією.
　　　
　　　
　　　
　　　
　　　
　　　
　　　
　　　
　　　
　　　
　　　
Рисунок 3.2 - Діаграма діяльності (Activity Diagram)
　　　Етап 1: Ініціалізація
　　　Цей етап виконується одноразово при подачі живлення на пристрій.
　　　Увімкнення та налаштування: Після старту ESP32 ініціалізує GPIO порти для роботи з LED-індикаторами.
　　　Підключення до мережі: Пристрій намагається встановити з'єднання з WiFi.
　　　Успіх: Вмикається індикатор LED WiFi, процес переходить до реєстрації.
　　　Помилка: Індикатор вимикається, помилка логується, і робота пристрою зупиняється (або переходить у режим очікування перезавантаження).
　　　Реєстрація: Виконується POST-запит до API для реєстрації пристрою. У разі успіху пристрій отримує унікальний DeviceID, необхідний для подальшої ідентифікації.
　　　Етап 2: Перевірка статусу
　　　Після успішної реєстрації пристрій визначає свою роль у системі.
　　　Запит призначення: Пристрій відправляє GET-запит, щоб дізнатися, чи прив'язав власник цей трекер до конкретної собаки.
　　　Обробка відповіді:
　　　Собака призначена: Зберігається DogID, що дозволяє активувати функції моніторингу геозони.
　　　Собака не призначена: Пристрій переходить у режим очікування, де активні лише базові функції, а специфічна логіка (геозона) буде пропущена.
　　　Етап 3: Головний робочий цикл
　　　Це нескінченний цикл (loop), який виконується до вимкнення живлення.
　　　Зчитування сенсорів: Використовується паралельне виконання (Fork) для одночасного отримання даних:
　　　GPS: Симуляція руху за алгоритмом Random Walk.
　　　Батарея: Симуляція поступового розряджання (-0.1% за ітерацію).
　　　Логіка Геозони (Geofence Logic): Цей блок виконується, тільки якщо собака призначена.
　　　Обчислюється відстань до центру безпечної зони (формула Haversine).
　　　Перевірка меж:
　　　НЕБЕЗПЕКА (Відстань > Радіус): Система перевіряє, чи було вже відправлено сповіщення. Якщо ні — відправляє POST-запит DangerZone і встановлює прапорець alert_sent = true. Це запобігає спаму сповіщеннями.
　　　БЕЗПЕЧНО: Якщо собака повернулася і прапорець alert_sent активний, він скидається (false).
　　　Відправка телеметрії: Всі зібрані дані (координати, заряд, статус) відправляються на сервер через PUT-запит.
　　　Індикація та сон:
　　　В залежності від успіху відправки телеметрії, LED Status вмикається або вимикається.
　　　Пристрій "засинає" на заданий інтервал (Sleep Interval) для економії енергії перед наступною ітерацією.
　　　Діаграма демонструє стійкість алгоритму: передбачено обробку втрати зв'язку та логіку запобігання дублюванню тривожних повідомлень.
