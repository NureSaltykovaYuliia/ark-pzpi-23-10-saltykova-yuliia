1  ОПИС ІНЖЕНЕРНИХ РІШЕНЬ
　　　1.1. Архітектура розгортання системи
　　　Для забезпечення надійності, масштабованості та простоти обслуговування було обрано мікросервісний підхід до розгортання з використанням контейнеризації.
　　　Схема розгортання включає наступні рівні:
　　　Інфраструктурний рівень (Cloud Provider): Використано Google Cloud Platform (GCP). Для хостингу створено віртуальну машину (Compute Engine instance) з параметрами e2-medium (2 vCPU, 4 GB RAM), що є оптимальним балансом між продуктивністю та вартістю для навчального проекту. Операційна система — Ubuntu 22.04 LTS.
　　　
　　　Рисунок 1.1 - Віртуальна машина
　　　
　　　Рівень контейнеризації (Docker): Всі компоненти бекенду упаковані в Docker-контейнери. Це гарантує, що програмне забезпечення працюватиме ідентично як на локальному комп'ютері розробника, так і на хмарному сервері, усуваючи проблему "it works on my machine".
　　　
　　　
　　　Рисунок 1.2 - Версія Docker
　　　
　　　Рівень оркестрації (Docker Compose): Для управління життєвим циклом контейнерів та їх мережевою взаємодією використано інструмент docker-compose. Він дозволяє декларативно описати конфігурацію сервісів, мереж та томів (volumes) в одному YAML-файлі.
　　　
　　　Рисунок 1.3 - Версія Docker Compose
　　　
　　　Рівень доступу (Reverse Proxy): Веб-сервер Nginx налаштовано як зворотний проксі-сервер. Він приймає всі вхідні запити на стандартний порт 80 і перенаправляє їх на відповідні внутрішні сервіси (API на порт 8080 або статичні файли клієнта).
　　　1.2. Обґрунтування вибору технологій
　　　При проектуванні середовища розгортання було прийнято ряд технологічних рішень:
　　　Серверна ОС Ubuntu Linux: Обрана через її стабільність, широку підтримку спільноти та нативну сумісність з інструментами контейнеризації. Більшість хмарних інструментів оптимізовані саме під Linux-середовище.
　　　База даних SQLite: Для поточної ітерації проекту використано SQLite. На відміну від клієнт-серверних СУБД (PostgreSQL, SQL Server), SQLite не вимагає окремого процесу для роботи, зберігаючи дані в одному файлі. Це спрощує бекап (копіювання одного файлу) та зменшує споживання оперативної пам'яті сервера.
　　　Docker Multi-stage build: У Dockerfile реалізовано багатоетапну збірку.
　　　Етап 1 (Build): Використовує повний SDK образ (.NET SDK), який містить компілятори та інструменти збірки. Він важкий (~800 МБ), але необхідний для компіляції.
　　　Етап 2 (Runtime): Використовує лише ASP.NET Runtime образ, який містить тільки необхідні для запуску бібліотеки.
　　　Результат: Фінальний образ займає лише ~200 МБ замість гігабайта, що пришвидшує завантаження та економить місце на диску.

　　　1.3. Конфігурація середовища та безпека
　　　Налаштування персистентності даних: Оскільки контейнери є ефемерними (всі дані всередині них зникають після перестворення), критично важливим є налаштування Docker Volumes. У файлі docker-compose.yml налаштовано mapping: ./Infrastructure/DB_Storage:/app/data:rw. Це означає, що файл бази даних фізично зберігається на жорсткому диску віртуальної машини, а контейнер лише отримує до нього доступ. Це гарантує збереження даних користувачів навіть при повному видаленні контейнерів.
　　　Безпека мережі: На рівні Google Cloud Firewall налаштовано правила, що дозволяють вхідний трафік тільки на порти 80 (HTTP) та 22 (SSH). Порт 5102 був відкритий для прямого тестування API, але в продакшн-середовищі доступ має відбуватися виключно через Nginx (порт 80), який приховує реальну структуру внутрішньої мережі.

　　　Основна бізнес-логіка зосереджена в сервісах. Нижче наведено реалізацію сервісу SmartDeviceService, який відповідає за обробку даних від нашийників.
　　　Файл: SmartDeviceService.cs
　　　Цей код демонструє реєстрацію пристрою та обробку телеметрії. Важливим моментом є розрахунок пройденої дистанції за допомогою формули Haversine, яка враховує кривизну Землі при обчисленні відстані між GPS-координатами.
public class SmartDeviceService : ISmartDeviceService
{
    private readonly ISmartDeviceRepository _deviceRepository;

    // Реєстрація пристрою. Якщо пристрій з таким GUID вже є - повертаємо його,
    // інакше створюємо новий запис.
    public async Task<SmartDeviceDto> RegisterDeviceAsync(string deviceGuid)
    {
        var existingDevice = await _deviceRepository.GetByDeviceGuidAsync(deviceGuid);
        if (existingDevice != null)
        {
            return MapToDto(existingDevice);
        }

        // Ініціалізація нового пристрою
        var device = new SmartDevice
        {
            DeviceGuid = deviceGuid,
            DogId = null, // Спочатку пристрій нікому не належить
            LastLatitude = 0,
            LastLongitude = 0,
            BatteryLevel = 100,
            TotalDistance = 0
        };

        var createdDevice = await _deviceRepository.AddAsync(device);
        return MapToDto(createdDevice);
    }

    // Оновлення телеметрії. Викликається IoT пристроєм періодично.
    public async Task UpdateDeviceTelemetryAsync(int id, UpdateSmartDeviceDto deviceDto)
    {
        var device = await _deviceRepository.GetByIdAsync(id);
        
        // Якщо є попередні координати, розраховуємо пройдену відстань
        if (device.LastLatitude != 0 && device.LastLongitude != 0)
        {
            double distance = CalculateDistance(
                device.LastLatitude, device.LastLongitude,
                deviceDto.LastLatitude, deviceDto.LastLongitude
            );
            device.TotalDistance += distance;
        }

        // Оновлюємо стан
        device.LastLatitude = deviceDto.LastLatitude;
        device.LastLongitude = deviceDto.LastLongitude;
        device.BatteryLevel = deviceDto.BatteryLevel;

        await _deviceRepository.UpdateAsync(device);
    }

　　　Для керування системою реалізовано спеціальний контролер AdminCodesController. Він захищений механізмом авторизації на основі ролей (RBAC).
　　　Файл: AdminCodesController.cs

[ApiController]
[Route("api/[controller]")]
[Authorize(Roles = "Admin")] // Ключовий атрибут безпеки: доступ тільки для ролі Admin
public class AdminCodesController : ControllerBase
{
    private readonly IAdminCodeService _adminCodeService;

    // Метод для генерації нового коду запрошення адміністратора
    [HttpPost]
    public async Task<IActionResult> CreateAdminCode()
    {
        try
        {
            var createdCode = await _adminCodeService.CreateAdminCodeAsync();
            return Ok(new {
                code = createdCode.Code,
                message = "Код адміністратора створено успішно"
            });
        }
        catch (Exception ex)
        {
            return BadRequest(new { message = ex.Message });
        }
    }

    // Спеціальний метод "Bootstrap". Працює без авторизації, але
    // дозволяє створити адміна ТІЛЬКИ якщо в системі ще немає жодного адміна.
    [HttpPost("initialize")]
    [AllowAnonymous]
    public async Task<IActionResult> CreateFirstAdminCode()
    {
        try
        {
            var createdCode = await _adminCodeService.CreateFirstAdminCodeAsync();
            return Ok(new { code = createdCode.Code });
        }
        catch (Exception ex)
        {
            // Поверне помилку, якщо адміни вже існують
            return BadRequest(new { message = ex.Message });
        }
    }
}

　　　4 ГРАФІЧНІ ІЛЮСТРАЦІЇ
　　　
　　　4.1. Опис архітектури системи
　　　Архітектура програмної системи MyDogSpace побудована за принципами "Clean Architecture" (Чиста Архітектура) з чітким розподілом відповідальності між чотирма основними шарами. Така структура забезпечує незалежність бізнес-логіки від зовнішніх фреймворків, інтерфейсів користувача та баз даних, що спрощує тестування та подальшу підтримку системи.




　　　Рисунок 4.1 - Архітектура системи
　　　
　　　　Діаграма ілюструє наступні шари та їх взаємодію:
　　　　1. Presentation Layer (Шар представлення):
　　　　Відповідальність: Цей шар є точкою входу для взаємодії із зовнішнім світом (клієнтами). Він приймає HTTP-запити, валідує їх та перенаправляє до бізнес-логіки.
　　　　Компоненти:
　　　　Controllers (ASP.NET Core Controllers): Обробляють REST API запити.
　　　　SignalR Hubs: Забезпечують двосторонній зв'язок у реальному часі (наприклад, для чатів).
　　　　Middleware: Проміжне ПЗ для обробки запитів (аутентифікація, логування).
　　　　API Endpoints: Визначені маршрути доступу до ресурсів.
　　　　Технології: ASP.NET Core Web API, JWT Authentication, Swagger Documentation.
　　　　Залежності: Шар представлення залежить від (використовує) шару Application Layer.
　　　　2. Application Layer (Шар застосунку):
　　　　Відповідальність: Містить сценарії використання (Use Cases) та специфічну бізнес-логіку застосунку. Він виступає посередником між представленням та інфраструктурою/доменом.
　　　　Компоненти:
　　　　Services: Класи, що реалізують бізнес-логіку (наприклад, SmartDeviceService, AuthService).
　　　　DTOs (Data Transfer Objects): Об'єкти для передачі даних між шарами, що дозволяє приховати внутрішню структуру доменних моделей.
　　　　Interfaces: Абстракції (контракти), які реалізуються в шарі інфраструктури (принцип інверсії залежностей)
　　　　Залежності: Шар застосунку залежить від Domain Layer та визначає інтерфейси, які реалізує Infrastructure Layer.
　　　　3. Infrastructure Layer (Шар інфраструктури):
　　　　Відповідальність: Забезпечує технічну реалізацію доступу до даних та взаємодію із зовнішніми сервісами. Це деталі реалізації, які приховані від бізнес-логіки.
　　　　Компоненти:
　　　　DbContext: Контекст бази даних Entity Framework Core.
　　　　Repositories: Реалізація інтерфейсів репозиторіїв для доступу до даних.
　　　　Migrations: Інструменти для управління схемою бази даних.
　　　　Data Access: Безпосередня взаємодія з SQLite Database.
　　　　Технології: Entity Framework Core, Repository Pattern.
　　　　Залежності: Шар інфраструктури залежить від Domain Layer (знає про сутності) та реалізує інтерфейси, визначені в Application Layer.
　　　　4. Domain Layer (Доменний шар):
　　　　Відповідальність: Ядро системи. Містить бізнес-правила та логіку, яка є незмінною незалежно від технологій (бази даних, UI).
　　　　Компоненти:
　　　　Entities/Models: Основні бізнес-об'єкти (наприклад, User, Dog, SmartDevice).
　　　　Enums: Перерахування (типи подій, ролі користувачів).
　　　　Domain Logic: Логіка, вбудована безпосередньо в сутності.
　　　　Особливість: Цей шар не має зовнішніх залежностей. Він є найбільш стабільним компонентом системи.
　　　　Потік залежностей: Як показано стрілками на діаграмі, залежності спрямовані всередину, до центру (до Доменного шару). Це означає, що Domain Layer нічого не знає про зовнішні шари, тоді як зовнішні шари (Presentation, Infrastructure) залежать від внутрішніх. Такий підхід робить систему гнучкою та легкою для модифікації.
　　　　
　　　4.2. Опис діаграми взаємодії компонентів (Sequence Diagram)
　　　Діаграма послідовності (Sequence Diagram) деталізує динаміку взаємодії між основними компонентами системи MyDogSpace: Користувачем, Веб-клієнтом, IoT пристроєм, API Сервером та Базою даних. Вона ілюструє три ключові сценарії використання системи.
　　　　
　　　　
　　　
　　　Рисунок 4.2 - Діаграма взаємодії компонентів
　　　1. Взаємодія Веб-клієнта (Користувача):
　　　Ініціація: Користувач відкриває додаток у браузері, що ініціює запит на отримання списку своїх собак.
　　　Обробка: Веб-клієнт надсилає GET /api/dogs/my запит до API Сервера.
　　　Доступ до даних: API Сервер виконує SQL-запит SELECT до бази даних SQLite, щоб знайти собак, прив'язаних до поточного OwnerId.
　　　Результат: Отримані дані повертаються у форматі JSON, і Веб-клієнт відображає список собак користувачу.
　　　2. Взаємодія IoT пристрою (Автономна робота):
　　　Реєстрація: При першому запуску IoT пристрій надсилає POST запит на реєстрацію. Сервер створює новий запис у таблиці SmartDevices та повертає унікальний ID.
　　　Цикл опитування (Loop): Пристрій входить у цикл, де кожні 5 секунд перевіряє свій статус. Він надсилає GET запит, щоб дізнатися, чи призначив власник цей пристрій собаці (Assignment status).
　　　Телеметрія: Якщо пристрій активний, він надсилає дані GPS та рівень батареї через PUT запит. Сервер оновлює відповідні поля (LastLatitude, LastLongitude тощо) в базі даних та повертає статус 204 No Content (успішне оновлення без тіла відповіді).
　　　
　　　
　　　3. Перегляд даних IoT Користувачем:
　　　Запит: Користувач хоче побачити, де знаходиться його собака. Веб-клієнт надсилає запит GET /api/smartdevices/dog/{dogId}.
　　　Вибірка: API Сервер запитує у БД останню відому телеметрію для конкретної собаки.
　　　Відображення: Сервер повертає об'єкт з координатами та станом батареї, який Веб-клієнт використовує для відображення маркера на карті.
　　　Ця діаграма чітко демонструє асинхронну природу системи: IoT пристрій постійно оновлює дані у фоновому режимі, а користувач отримує актуальний стан системи на вимогу (on-demand).
